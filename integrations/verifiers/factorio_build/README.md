# factorio-build

Requires `verifiers>=0.3.1` and `factory-sim>=0.2.0`, installed from PyPI with
prebuilt wheels.

The model writes one Python program, `def build(world):`, that builds a
working factory in [factory-sim](https://github.com/divagr18/factory-sim), a
tick-exact simulator of Factorio's early game. The program runs on scenes it
has never seen, and the reward is the fraction of them where the factory
verifiably produces. The program sees only what a trained RL policy sees, and
every call it makes is one decision of that policy's action space. The
simulator is checked against the real game by
[FactorioGym](https://github.com/divagr18/FactorioGym).

## Tasks

`task` (`sim_task` in the v1 config) picks one of two tasks.

| Task | The program has to | A scene succeeds when | Decisions |
| --- | --- | --- | --- |
| `construct_smelting_line` (default) | walk to an iron patch it can only partly see, choose a layout that avoids walls and water, place a burner drill on ore and a stone furnace under the drill's drop point, and fuel both | at least 10 iron plates are made by machine during a verification minute | 600 |
| `belt_smelting` | walk between an iron patch, a coal patch and a wooden output chest, 20 to 40 tiles apart, and build a line of drills, furnaces, transport belts and burner inserters that carries plates into the chest | at least 150 iron plates reach the chest during a ten-minute window in which the program cannot act | 2,500 |

`belt_smelting` starts with 4 burner drills, 4 stone furnaces, 40 belts, 10
burner inserters and 20 coal. Twenty coal runs a line for about 79 plates, so
the line also needs coal from the coal patch, mined by hand or by a drill.
Plates smelted from hand-mined ore do not count. Programs on this task hold a
larger `world` (the v3 profile): public markers for the three sites,
`mine_resource`, `rotate`, `take_fuel`, `finish`, belt lanes, and each
inserter's pickup and drop points. The prompt lists the whole API and the
measured mechanics.

The task is FactorioGym's `belt_smelting` 1.1.0, ported draw for draw. Its
reference solver delivers 150 plates in 200 of 200 episodes on the real game,
and its port (`fsim.belt_expert`) in 599 of the first 600 simulator scenes; the
one failure has its whole coal patch on water.

## Taskset

- **Source:** scenes generated by `fsim.scenes.sample`, draw for draw identical
  to FactorioGym's generator.
- **Rows:** each row is a block of `n_scenes` consecutive scenes (default 16)
  from one split.
- **Splits:**
  - `train`: seeds 0-99,999, the training layout families (four for
    `construct_smelting_line`; `open`, `walled` and `split_patch` for
    `belt_smelting`).
  - `val`: seeds from 100,000 on, same families.
  - `holdout`: families neither of the others contains (`obstructed_patch`;
    `obstructed` and `far_chest`). Its first 100 scenes are FactorioGym's
    frozen holdout. Evaluation only: it is built only when asked for, and never
    as a training reward.
- **Reward:** `success_rate`, the fraction of the row's scenes solved, plus
  `format` at weight 0.1: +1 for a program the sandbox accepts, -1 for one it
  refuses, 0 for no program. An optional `refusal_penalty` is off by default.
- **Sandbox:** a static AST allowlist. No imports, no reflection, no attribute
  starting with `_`; at most 300 lines; 2 s per scene. The rules are stated in
  the prompt.
- **Scoring cost:** well under a second of CPU per 16-scene row for
  `construct_smelting_line`, and about a second for `belt_smelting`, in local
  worker processes. No GPU, container or network.
- **Validation:** `validate factorio-build --only-gold` checks that each row
  is solvable: with the seed builder program for `construct_smelting_line`,
  and with the reference builder for `belt_smelting`.
- **Entry points:** the v1 taskset (`FactorioBuildTaskset`, Linux and macOS)
  and the v0 `load_environment`. Both score with the same function.

## Prompt versions

`prompt_version` sets the last line of the user message.

- `v1` (default): a plan of at most five lines, then the program. The
  baselines below and the SFT-800 recipe used it.
- `v2`: think the problem through step by step in plain prose, then the
  program. The Evolve & Reinforce warm start trains on replies that reason, so
  it asks for them.

## Run it

Install from the Hub:

```bash
prime env install divagr/factorio-build
```

The v0 entry point (`vf-eval`, `prime eval run`) takes `load_environment`'s
arguments as JSON:

```bash
prime eval run factorio-build -m openai/gpt-6-luna -n 32 -r 1 -a '{"split": "val"}'
prime eval run factorio-build -m openai/gpt-6-luna -n 8 -r 1 \
    -a '{"task": "belt_smelting", "split": "val", "prompt_version": "v2"}'
vf-eval factorio-build -m openai/gpt-6-luna -n 6 -r 1 -a '{"split": "holdout"}'   # evaluation only
```

The v1 taskset:

```bash
uv run eval factorio-build -m openai/gpt-6-luna -n 32 -r 1 --env.taskset.split val
uv run eval factorio-build -m openai/gpt-6-luna -n 8 -r 1 \
    --env.taskset.sim-task belt_smelting --env.taskset.prompt-version v2
uv run validate factorio-build --only-gold --runtime.type subprocess --taskset.num-examples 4
```

The v1 commands default to the `prime` runtime, which needs `prime login`.
`--runtime.type subprocess` runs `validate` locally; in an eval
config, `env.agent.runtime.type = "subprocess"` does the same (the recipe's
[`eval.toml`](https://github.com/divagr18/factory-sim/tree/main/recipes/grpo-factorio-build/configs)).

Training with [prime-rl](https://github.com/PrimeIntellect-ai/prime-rl): name
the taskset in the config, as the recipe's
[configs](https://github.com/divagr18/factory-sim/tree/main/recipes/grpo-factorio-build/configs)
do, and set `FACTORIO_BUILD_MAX_POOLS` (for example to 7) so concurrent
rollouts are scored in parallel instead of queueing behind one pool:

```toml
[[source]]
name = "factorio-build"
env.taskset.id = "factorio-build"
env.taskset.split = "train"
env.taskset.sim_task = "construct_smelting_line"   # or "belt_smelting"
env.taskset.prompt_version = "v2"
env.taskset.task.workers = 4
```

The full SFT + GRPO recipe, with its deploy scripts and the fixes it needed,
is [`recipes/grpo-factorio-build`](https://github.com/divagr18/factory-sim/tree/main/recipes/grpo-factorio-build).

## Results

Every number in the two tables is scored in the simulator, on
`construct_smelting_line`.

**Zero-shot baseline.** One reply per row, game notes on, 16 scenes per row,
`prompt_version` v1, and up to 32,000 completion tokens, reasoning included.

| Model | `val` scenes solved (32 rows) | `holdout` scenes solved (6 rows) | Programs accepted | Rows fully solved |
| --- | --- | --- | --- | --- |
| `gpt-6-luna` | 80.9% | 89.6% | 97% val, 100% holdout | 16/32 val, 2/6 holdout |

The `val` rows are subsets 0-31 at `seed=0`; the `holdout` rows are 0-5,
frozen indices 0-95. Six rows is a small sample. Almost every remaining
failure is a valid program whose plan fails on some scenes.

**Trained Qwen3.5-9B.** 16 rows x 4 samples x 8 scenes per split, temperature
0.6, thinking off. PlanBench is Blocksworld plan generation (task 1) and plan
execution (task 7), 500 instances each, thinking off. It measures how much
general planning a recipe costs the model.

| Qwen3.5-9B | `val` (sim) | `holdout` (sim) | PlanBench generation | PlanBench execution |
| --- | --- | --- | --- | --- |
| base | 2.1% | 1.6% | 53.2 | 39.8 |
| SFT-800 + GRPO (earlier recipe) | 85.9% | 84.0% | 2.8 | 3.0 |
| Evolve & Reinforce, round 1 | 85.6% | 71.9% | 46.4 | 27.8 |

Base Qwen3.5-9B solves almost nothing: half its programs exceed the sandbox's
size limit and most of the rest fail to parse. The earlier recipe fine-tuned
it on 800 bare programs found by program search, then ran GRPO. It reached
84.0% on the holdout, and PlanBench fell to 2.8 and 3.0. Evolve & Reinforce
builds its warm start from the model's own explanations of those programs
(prompt v2), mixes in replay of the base model's answers to general prompts,
then runs GRPO. PlanBench stays at 46.4 and 27.8, and the holdout is 12 points
lower.

Models: [`qwen3.5-9b-factorio-build-er-r1`](https://huggingface.co/divagr1925/qwen3.5-9b-factorio-build-er-r1)
(Evolve & Reinforce, round 1) and its warm start
[`qwen3.5-9b-factorio-build-er-r1-sft`](https://huggingface.co/divagr1925/qwen3.5-9b-factorio-build-er-r1-sft).
All models: [models collection].

**On the real game.** A random 16 of the SFT-800 + GRPO model's holdout
programs, each on 10 holdout scenes, succeed in 136 of 160 episodes on
Factorio 2.0.60, and the simulator gives the same outcome in every episode.
Programs from program search succeed in 397 of 400 engine episodes (99.3%),
again matching the simulator in every episode. The evidence files are in
FactorioGym.

## Config

v1 fields are `--env.taskset.<name>`, with dashes for underscores.
`load_environment` takes the same names as keyword arguments, using `task` for
`sim_task` and flattening the task-level fields.

| Field | Default | Description |
| --- | --- | --- |
| `sim_task` | `construct_smelting_line` | `construct_smelting_line` or `belt_smelting` (`task` in `load_environment`) |
| `split` | `train` | `train`, `val` or `holdout` (evaluation only) |
| `n_scenes` | 16 | Scenes per row, 1 to 64 |
| `num_examples` | 64 | Rows |
| `seed` | 0 | First scene index of the split |
| `game_notes` | true | Include notes on mechanics: drop point, reach, fuel, belts and inserters |
| `prompt_version` | `v1` | `v1` (short plan, then the program) or `v2` (step-by-step prose, then the program) |
| `task.workers` | 4 | Simulator processes per env worker; 0 runs in-process, for trusted code only |
| `task.job_timeout_s` | 30 | Wall-clock limit per chunk of scenes; a hung worker is replaced |
| `task.decision_budget` | the task's own | Decisions per scene: 600 for `construct_smelting_line`, 2,500 for `belt_smelting` |

To enable the refusal penalty in v1:
`[env.taskset.task.rewards] refusal_penalty = { weight = 0.05 }`.

## Changelog

- 2026-09-26 (0.2.0): Adds `belt_smelting` (FactorioGym `belt_smelting`
  1.1.0) with its v3 `world`, and `prompt_version` (`v1`, the default, or
  `v2`). `decision_budget` now defaults to the task's own. `validate` checks
  `belt_smelting` rows with the reference builder. Two fixes to the v0
  `load_environment` under verifiers 0.3.1: the dataset no longer has a plain
  string `task` column, which failed every rollout, and scene seeds are stored
  as strings, because holdout seeds overflow Arrow's int64.
  `construct_smelting_line` rows, v1 prompts and scores are unchanged.
  Requires factory-sim 0.2.0.
- 2026-09-23 (0.1.1): The sandbox accepts ordinary Python that the prompt never
  forbade: `lambda`, `:=`, helper names with one leading underscore, and set
  and string methods. The prompt now states the attribute and naming rules.
  This requires factory-sim 0.1.2. Baselines are measured under these rules.
- 2026-09-23 (0.1.0): Initial release.
